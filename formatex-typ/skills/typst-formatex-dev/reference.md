# Template internals

Read this only when changing `main.typ`, `src/` or `components/`, or adding a component.

## How Markdown tags become Typst

`main.typ` is a few lines:

```typst
#import "src/prelude.typ": *                      // template names + the @preview packages
#show: doc => conf(doc)                           // src/conf.typ
#import "src/lib/mitex.typ": mitex                // wrapper applying mitex-fixes, then mitex-base
#import "src/preprocess/pipeline.typ": preprocess
#import "components/_registry.typ": html-tags, all-rules, scope-extras   // GENERATED
#show: all-rules                                  // show rules exported by components (<name>-rules)
#cmarker.render(preprocess(source-body), math: mitex,
  scope: (image: (source, ..args) => image(source, ..args), make-heading-numbering: make-heading-numbering) + scope-extras,
  html: html-tags)
```

- `source-body` (`src/core.typ`) = the source file (config `source` / `--input source`) without its front matter, every `<include>` line replaced by the included file (`expand-includes`). `preprocess` (`src/preprocess/pipeline.typ`) then drops `<!-- ... -->` comments (`strip-comments`), rewrites `{#id}` on headings and equations, Persian list numbers and `{...}` table/list lines.
- `components/_registry.typ` is generated by `tools/gen-registry.mjs` from `components/*.typ`: `html-tags` merges every `<name>-tags` (each wrapped by `wrap-tags` in `src/lib/schema.typ`, which checks the attributes against `<name>-schema` first), `scope-extras` merges the `<name>-scope` dictionaries, `all-rules` applies the `<name>-rules(doc)` functions in `// rules-order: N` order.
- Each key in `html-tags` is a tag name usable in any Markdown document. The callback gets `attrs` (dictionary of **string** values) and `body` (rendered content).
- Void tags (no closing tag, like `<img>`) are declared as `("void", attrs => ...)`.
- The `scope.image` override makes Markdown image paths resolve relative to the project instead of the cmarker package. Functions that preprocessors call from injected `<!--raw-typst ... -->` (`make-heading-numbering`, `list-block`) must be in `scope` too (`list-block` comes from `lists-scope` in `components/lists.typ`).
- **Paths.** Typst resolves a path relative to the file whose code calls `image()` / `read()` / `csv()` / `bibliography()`, not to the project. User-supplied paths are relative to the project root, so component and `src/` code wraps them in `root-path(...)` (`src/lib/basics.typ`; `rooted(...)` in `src/core.typ`) before the call.
- Where things live: shared helpers `src/lib/*.typ`, a helper used by one component stays in that component's file, preprocessors `src/preprocess/*.typ`.

## Parent/child tags

Child tags mark their content with metadata; the parent collects them:

```typst
caption: (attrs, body) => tag("caption", attrs, body),
fig: (attrs, body) => {
  let (tagged: captions, rest) = untag(body, "caption")  // captions: array of (attrs:, body:)
  ...
}
```

Use the same `tag` / `untag` helpers for any new parent/child component. Two child tags can share one kind and carry the difference in their attrs, as `<user>` / `<ai>` do: both are `tag("chat-msg", attrs + (role: "user" | "ai"), body)`, so `<chat>` gets them in document order.

## `<cetz>`

The code is evaluated with `eval(code, mode: "code", scope: (..dictionary(cetz.draw), cetz: cetz, theme: theme))` inside `cetz.canvas`, after `set-style(stroke: theme.fg)`. The tag returns `tag("drawing", (canvas: canvas), align(center, canvas))`; `<fig>` finds it with `find-tagged(rest, "drawing")`, takes the canvas from the metadata, and shrinks it with `measure` + `scale(reflow: true)` by `calc.min(1, region.width / size.width, height factor, width factor)`: always fitted to the line width, also fitted to `height`/`width` when given, never enlarged.

## `<tree>` and `<chart>`

- Handlers: `tree` reads `read(attrs.src)` or `find-raw(body).text` and returns `caption-figure(attrs, "tree", tree-block(attrs, source))`. `chart` asserts `dir` in `rtl ltr auto`; for a forced `dir` it pushes the value onto `dir-stack` around `caption-figure(attrs, "chart", chart-block(attrs, body))` and pops it afterwards, so the caption, figure supplement and `resolve-dir` all see it.
- Chart geometry is laid out with `set text(dir: ltr)` inside `layout` (so `place` anchors on the left) and mirrored for RTL with `fx(x, w) = full-w - x - w`: categories run right to left, ticks and the y title sit on the right, and pie angles use `side = -1` (counter-clockwise). Labels keep their own direction via `content-dir` (`label-text`).
- Both are figures of `kind: image`, so `figure-list` (`<lof>`) and `reference-text` handle them without changes.

## Mermaid

- Import: `#import "@preview/mmdr:0.2.2": mermaid-svg` in `src/prelude.typ` (mmdr = WASM build of mermaid-rs-renderer; layout is its own, not mermaid.js).
- `mermaid-diagram(code)` calls `mermaid-svg(code, theme: (...))` with every color derived from `theme` (`tint(c, p)` = `color.mix((c, p), (theme.bg, 100% - p))` as hex): `primary_color` / `sequence_actor_fill` = accent tint (10%, 18% on dark), `primary_border_color` / `sequence_actor_border` = 70% accent, `line_color` / `sequence_actor_line` = `muted`, `secondary_color` / `sequence_note_fill` = secondary tint, `tertiary_color` / `cluster_background` / `sequence_activation_fill` = `code-bg`, `cluster_border` / `sequence_activation_border` / `pie_outer_stroke_color` = `rule`, `edge_label_background` / `background` / `pie_stroke_color` = `bg`, all text colors = `fg`. `font_family` = first Persian font, `font_size` / pie section + legend = `12 * zoom`, pie title `15 * zoom`. `pie_colors` must have **exactly 12** entries (mmdr requirement): accent / secondary tints alternating, 60% → 6%. These override any `%%{init}%%` theme directive. Mindmap ignores them (mmdr's own palette).
- `mermaid-lines(svg)`: mmdr writes a wrapped label as `<text x y ...><tspan x dy>line</tspan>...</text>`; Typst's SVG renderer (usvg) lays such multi-line RTL text over itself. The regex rewrite emits one `<text>` per line with absolute `x` (the tspan's or the text's) and `y` (accumulated `dy`), keeping the other attributes minus `font-family`. A line matching `\p{Arabic}` gets the Persian font and is wrapped in RLM (`U+200F`) on both ends so trailing punctuation stays at the right; other lines get the Latin font. Result → `image(bytes(...), format: "svg")`.
- Size options: cmarker passes the whole fence info string as `raw.lang` (` ```mermaid width=60% height="4cm" ` → `lang: "mermaid width=60% height=\"4cm\""`). `mermaid-options(r)` checks `lang` matches `^mermaid(\s|$)`, tokenizes the rest as `key=value` / `key="value"` (asserting nothing else is left and every key is `width` or `height`) and converts values with `parse-length`. Sizes go to `image(width:, height:, fit: "contain")`, so the diagram is enlarged or shrunk like an image; with both it fits inside the box. Without a size, `mermaid-block` wraps the natural-size image in `fit-width`.
- Standalone blocks: `#show raw.where(block: true): it => { if mermaid-options(it) == none { return it }; context align(align-names.at(inherited-align("center")), mermaid-block(it)) }`. A filter on `lang: "mermaid"` would miss blocks with options (their `lang` is the whole info string), hence the general rule that hands other blocks back unchanged so `src/core.typ`'s code-block rule still applies.
- In `<fig>`: if `find-tagged(rest, "drawing")` is empty, `find-raw(rest)` is kept as `mermaid` when `mermaid-options(r) != none`; the picture is `mermaid-block(mermaid, ..sizes)` where `sizes` = the `<fig>`'s non-`none` `width` / `height` (they win over the fence's). Mermaid in `<fig>` is therefore image-like (enlarge or shrink); `<cetz>` drawings keep the shrink-only branch; `ratio` is ignored for both.
- Syntax errors are not raised by mmdr: the diagram comes out empty or partial.

## Labels and references

- `<fig id>` attaches `label(id)` to the `figure`; theorem blocks attach it to a `metadata` element placed before the block; headings get cmarker's GitHub-style slug labels (ZWNJ and punctuation removed).
- `heading-ids(src)` preprocesses the Markdown before `cmarker.render`: a heading line ending in `{#id}` loses the suffix and is followed by `<!--raw-typst #metadata((heading-id: "id"))<id> -->`. cmarker has no heading attributes, and labelling the heading itself would clash with its slug label ("content labelled multiple times"). Fenced code blocks are skipped.
- `link-free-id(title)` inside `heading-ids`: cmarker's slug keeps the text of links in the title, while hand-written `#slug` links usually leave them out. A heading line that contains `](` (a Markdown link or image) and has no explicit `{#id}` is followed by an extra `<!--raw-typst #metadata((heading-id: "slug"))#label("slug") -->`, where slug = the title without its `#` marks and without every `!?[...](...)`, lowercased, characters other than `\p{L}\p{M}\p{N}_-` and space removed, trimmed, spaces → `-` (`### پلتفرم Papers With Code ([paperswithcode.com](https://...))` → `پلتفرم-papers-with-code`). Applied both to plain heading lines and to headings with `{key=value}` options but no `#id`.
- `<ref>` runs `query(label(to))`, falling back to the slugified `to`. If it finds `heading-id` metadata it switches to the last heading before it, then links to `el.location()`.
- Inside inline content `text.dir` is not yet the paragraph's direction (paragraph show rules run after inline realization). Use `last-dir.get()` for the language of the surrounding paragraph, as `<ref>` does.
- `<bibliography>` sets `show grid.cell` to give each entry its own direction when `dir = "auto"`.

## Cover page

`cover-page()` in `src/page.typ` reads `[cover]`, builds a `page(numbering: none, header: none, ...)` and resets `counter(page)` to 0 inside it so the next page is 1. `conf` inserts it before the document when `sys.inputs.cover` (or `[cover] enabled`) is true.

## Theme dictionary keys

`dark` (bool), `bg`, `fg`, `heading`, `muted`, `accent` (quote bar), `secondary` (soft background tints: table header rows, highlighted code lines; = `accent` except in zinc), `rule` (lines/table rules/default borders), `code-bg`, `code-stroke`. Use these instead of hard-coded colors in new components so all eight themes work. For user-supplied pastel colors on dark themes, mix toward `theme.bg` as `<alert>` does.

To add a theme: add an entry to `src/themes.typ` with all keys and list it in the `config.toml` comment.

## Direction pitfalls

- Anything that chooses a direction from content must call `content-dir(body)` inside `context` (or `resolve-dir`), never `text-dir` directly; otherwise it ignores the `dir` setting and `<dir>`. Exceptions on purpose: `<cetz>` labels (`directed-content`), Mermaid labels and `<kbd>` keep their own per-label direction; page furniture uses `doc-text-dir`.
- The `table.cell` and `quote` show rules in `src/conf.typ` are `context` and use `content-dir`; `<alert>`'s icon layout is wrapped in `context` for the same reason.

- A container that does not span the full width can shrink RTL paragraphs and push them left. Give inner blocks `width: 100%` and set `text(dir: ...)` on the container (see `<alert>`).
- Typst grids mirror in RTL: cell `x: 0` is the right-most column.
- Typst pads outline indentation on the physical left; `<toc>` pads manually on the right for RTL entries.
- Mixed-direction strings inside a forced-direction line need Unicode isolates (`\u{2066}` LRI / `\u{2067}` RLI ... `\u{2069}` PDI), as `<toc>` does.

## Checklist for a new component

Short version; the full rules (direction, alignment, colors, pitfalls, testing) are in [extending.md](extending.md).

1. Create `components/<name>.typ` (see [extending.md](extending.md#adding-a-component)); the registry is generated.
2. Parse attributes with `parse-length` / `parse-ratio`; give defaults with `attrs.at(key, default: ...)`.
3. Use `theme.*` colors.
4. Handle direction (`resolve-dir` inside `context`) if the layout depends on it.
5. Add the tag to the component's `<name>-schema` (attributes, types, allowed values; see extending.md) and a usage example to `examples/demo.md` (not the guides `docs/doc_en.md` / `docs/doc_fa.md`), compile with `--input source=examples/demo.md`, and inspect the rendered page.
6. Document the component in `SKILL.md`.
7. **Mandatory Documentation & Skill Synchronization:** Update both user guides (`docs/doc_en.md` and `docs/doc_fa.md`) and the authoring skill (`skills/bilingual-document-authoring/components.md` and `config.md`). Whenever possible, delegate this synchronization task to a subagent (`invoke_subagent`).
